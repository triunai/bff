# 0002 — v0.1.0 publication

Date: 2026-10-05 · Version: 0.1.0

## What changed
BFF became a public MIT repo (`triunai/bff`) with a release:
- A sanitised source tree: CLI, fresh-repo templates, four skills, prebuilt Osiris plugin, no private history.
- A release builder (`scripts/build-bff-release.py`) that only packs files listed in `release-files.json` and writes `bff-0.1.0.tar.gz`, `SHA256SUMS` and an inventory manifest inside the archive.
- An archive canary: the builder refuses machine-specific home paths and credential-shaped content, and `tests/test_release.py` proves it by planting canaries and checking the build fails.
- A one-line installer, `curl -fsSL https://raw.githubusercontent.com/triunai/bff/v0.1.0/install.sh | sh`. It downloads the release archive, checks the SHA256 and the file inventory, keeps each version under `~/.local/share/bff/releases/` and links `~/.local/bin/bff`.
- GitHub release `v0.1.0` (annotated tag at `5c7caef`) with two assets: the archive and `SHA256SUMS`.

## Why
A "portable SDK" that only runs from the author's disk is not portable. The release is the proof that a stranger can install it, and the canary is the proof that the package does not carry private material.

## Decisions & alternatives rejected
- A declared file list instead of "everything in the repo". New files must be reviewed into `release-files.json`; an unlisted file under `bff/`, `templates/` or `plugins/` fails the build.
- Pin the installer to a tag (`/v0.1.0/install.sh`), not `main`. Rejected: an unpinned URL, because "latest main" can change under a user.
- Python standard library only; no runtime dependencies. Rejected: a packaged wheel or npm install, which would add a trust and tooling surface.
- Honest trust note: archive and checksum come from the same publisher, so this is not independent signing. The README says so. Rejected: implying a signature we do not have.
- Release symlinks refused at every layer (builder, installer, archive reader).

## What went wrong / surprised us
- The first public commit had a home-path check but no credential check. The follow-up `5c7caef` ("reject credential-shaped content with an archive canary") added patterns for private keys, GitHub tokens, Anthropic keys and AWS key ids, and a test that plants each one. Lesson: the check and the proof of the check must ship together.
- The canary tests build the release from a scratch copy of the tree. A canary that only greps the working tree would not prove the archive is clean.

## How it was verified
Recorded in the release notes at the time:
- 37 Python tests, 22 observer (TypeScript) tests with fresh dependencies.
- Archive install, reinstall and rollback exercised against a scratch prefix.
- Fresh-repo adoption (`bff init`, `check`, `hydrate`).
- Native browser checks of Osiris navigation, the Claude source, dark-theme cards and the actual diff and Back behaviour.
- Not claimed: remote CI, production enforcement. The notes say local evidence does not certify those.

## Lessons
- Ship a negative test for every safety rule: show the build fails when the bad thing is present.
- Pin what users run. Keep the install path boring.
- Say what a checksum does and does not prove.
