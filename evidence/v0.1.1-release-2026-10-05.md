## Owner's real install: upgraded in place
The installer supports it: it only replaces a command link that it owns (a symlink into `~/.local/share/bff/releases/<version>-<hash>/bin/bff`) and keeps the previous release. `sh /tmp/bff-install.sh` with the default prefix printed `previous_target` = the 0.1.0 release and `path_available: true`; `~/.local/bin/bff --version` now prints `bff 0.1.1`. The 0.1.0 releases remain under `~/.local/share/bff/releases/`; rollback is `python3 install.py --activate <release>`.

## Problem found after publishing: CI red on the release commit
The first GitHub Actions run (push of `7f4afcd`, run 37278897720) failed on Python 3.12: `tests/test_bff.py::test_install_reinstall_disable_activate` compared an installed-release tree before and after running its launcher, and that interpreter wrote `__pycache__` into the release directory (local macOS Python 3.9 does not). The product is fine (the installer's own inventory already ignores `__pycache__`); the test's snapshot helper was too strict. The 3.9 job was cancelled by fail-fast, so Python 3.9 on Linux was not observed.
Fix (test-only, not a weakened assertion: still byte-exact comparison of release content, only bytecode excluded): `tree()` skips `__pycache__`; recorded under `[Unreleased]` in CHANGELOG.md. The tag `v0.1.1` was NOT moved; it keeps the old test. The fix is pushed to main as a follow-up commit; its CI result is recorded at the end of this file.
